# SP2.5: harness robustness — completion signal, failure kinds, stall detection, context window, resume

**Date:** 2026-08-17
**Status:** Approved design (owner approved all six sections in chat)
**Origin:** The SP2 record (`docs/superpowers/bench/2026-08-16-sp2-worker-scoreboard.md`,
`-sdd-ledger.md` items 58, 62, 68, 72, 98). Every hard failure across 16 SP2 tasks was
the harness, not the model: fake `finish` tool calls aborted runs after the work was
committed (T6, T9a); an empty/think-only reply was reported as `completed` (T7b, Qwen3.6);
runs hit `max_turns` while spinning after the work was done (T7a fix1, T7b, T10 fix1);
`CONTEXT_WINDOWS` is a hard-coded table; a run that ends without finishing cannot be
picked up where it stopped.
**Parent spec:** `docs/superpowers/specs/2026-08-15-review-response-design.md` (v3.1).
SP2.5 sits between SP2 (shipped, 0.4.1) and SP3. Where SP3's plan already names a
piece of this work (`--context-window` in SP3 Task 6; the tool registry in SP3 Tasks 1–3),
SP2.5 lands it first and SP3 inherits it.

## Purpose

Make the runner loop end runs for the right reason. A model must have a legal way to say
"done"; a reply that carries no work must not count as completion; one kind of mistake
must not be scored as another; a worker that has stopped making progress must be stopped
with an honest status; the context window must be settable; and a run that ended early
must be resumable on the same worktree.

Everything here is Python-stdlib-only, keeps `schema_version` 2 (all transcript, stdout,
and `run.json` changes are additive), and changes no security property of SP2: the
container recipe, the export validator, the no-host-git-on-worker-content rule, and the
guardrails are untouched. The one new host→container data path (resume seeding, §5) moves
the operator's own worktree into a fresh container; it is the trusted direction.

## 1. Completion signal

### 1.1 The `finish` tool

`TOOL_SCHEMAS` gains:

```json
{"type": "function", "function": {"name": "finish",
  "description": "End the run. Call this once the task is complete and verified (tests/build run, changes committed if the task asked for commits). summary: 2-6 sentences on what you did and anything left undone.",
  "parameters": {"type": "object", "properties": {"summary": {"type": "string"}}, "required": ["summary"]}}}
```

`finish` is **terminal and runner-owned**: `ToolExecutor` does not know it (`_table` and
`_TOOL_PARAMS` are unchanged; the executor's `KeyError` path never sees it because the
runner intercepts the name first). In a turn that contains a `finish` call, the runner
executes every other tool call in order first (their results are appended and transcribed
as usual), then ends the run with status `completed` and
`final_message = str(args.get("summary", ""))`. Missing or non-string `summary` does not
fail the call — the run still ends; the transcript `tool_result` for `finish` records
`result="run finished"`. If a turn's `finish` call is malformed (bad JSON args), it is
counted like any malformed call (§2) and the run continues.

The system prompt's last rule changes from "reply WITHOUT calling any tools" to:

> When the task is complete, call `finish(summary=...)` with a short summary of what you
> did and anything left undone. A plain reply with no tool calls also ends the run.

The unknown-tool error becomes:
`ERROR: unknown tool '<name>'. Available: <list>. To end the run call finish(summary=...).`

### 1.2 Reply classification (no tool calls in the reply)

When a reply carries no structurally valid tool calls, the runner classifies it with
`classify_text_reply(content, finish_reason) -> str` (pure function, `runner.py`):

| Condition (checked in order) | Class |
|---|---|
| `finish_reason == "length"` | `truncated` |
| content, after removing every `<think>…</think>` block (DOTALL, unterminated `<think>` removes to end) and stripping whitespace, is empty | `empty` |
| stripped content contains any of `<tool_call>`, `<function=`, `<function_call>`, `<|tool_call|>`, or a `{`…`}` span that JSON-parses to an object with string `"name"` and a `"arguments"` key | `text_tool_call` |
| otherwise | `answer` |

`answer` → status `completed`, `final_message = content` (unchanged behaviour: a model
that never calls `finish` still completes exactly as before).

`truncated`, `empty`, `text_tool_call` → **not** completion. The runner appends a
`{"role":"user"}` nudge, transcribes a `nudge` event (§7), records an `empty_reply`
failure (§2), counts the turn as no-progress (§3), and loops. Nudge text by class:

- `truncated`: "Your reply was cut off at the token limit. Continue with smaller steps — emit one tool call at a time and write large files in pieces."
- `empty`: "Your reply contained no tool call and no answer. Continue the task with a tool call, or call finish(summary=...) if the task is complete."
- `text_tool_call`: "Your reply contained a tool call written as text; the harness only executes tool calls made through the tools API. Re-issue it as a real tool call."

The existing `messages.append(msg)` for the completed path stays; for the three
non-completion classes the assistant message is appended in canonical shape
(`{"role":"assistant","content": content or ""}`) before the nudge so history stays valid.

## 2. Failure counting, kind-aware

Replace the bare `failures` int with a small `FailureTracker` in `runner.py`:

```python
FAILURE_KINDS = ("malformed_entry", "malformed_args", "unknown_tool", "bad_args", "empty_reply")
MAX_CONSECUTIVE_FAILURES = 3      # per kind (name kept; meaning now per kind)
MAX_TOTAL_CONSECUTIVE_FAILURES = 6

class FailureTracker:
    def record(self, kind: str) -> str | None:
        """Increment kind and total; return the abort reason string, or None."""
    def reset(self) -> None:
        """Any successful tool execution clears every counter."""
```

`record` returns `f"aborted after {MAX_CONSECUTIVE_FAILURES} consecutive {kind} failures"`
when that kind's counter reaches `MAX_CONSECUTIVE_FAILURES`, or
`f"aborted after {MAX_TOTAL_CONSECUTIVE_FAILURES} consecutive tool failures"` when the
total reaches `MAX_TOTAL_CONSECUTIVE_FAILURES`; the runner returns
`finish("model_error", reason)` immediately when a reason is returned. Mapping from the
existing branches: malformed tool-call entries → `malformed_entry`; `json.JSONDecodeError`/
`ValueError` on arguments → `malformed_args`; `KeyError` from the executor → `unknown_tool`;
`TypeError` → `bad_args`; §1.2 non-completion replies → `empty_reply`. A successful
`executor.execute` calls `reset()` (today's `failures = 0`). Note a `finish` call
(§1.1) is not an executor success and does not reset — it ends the run.

## 3. Stall detection

A **turn made progress** if at least one of its executed tool calls was:

- `write_file` or `edit_file` whose result does not start with `ERROR`, or
- `bash` whose `(command, result)` pair has not been seen before in this run — the
  runner keeps a `set` of `sha256(command + "\0" + result)`.

Everything else is not progress: `read_file`, `list_dir`, `grep` (read-only), any tool
whose result starts with `ERROR`, a `bash` call repeating a command with identical output
(re-running the same failing test, `ls` in a loop), a `finish` call (irrelevant — the run
ends), and turns handled by §1.2 (no tool calls).

`ProgressTracker` in `runner.py`:

```python
class ProgressTracker:
    def __init__(self, stall_turns: int)
    def note_call(self, name: str, args: dict, result: str) -> None   # per executed call
    def end_turn(self) -> str | None
        # returns "nudge" once per idle streak, when idle_turns == stall_turns // 2 (and stall_turns >= 2),
        # "stalled" when idle_turns >= stall_turns, else None; progress resets idle_turns to 0
```

Runner: `Runner(..., stall_turns: int = 12)`. After each turn's tool calls are executed
(and after each §1.2 non-completion reply) call `end_turn()`. `"nudge"` → append the user
message "No progress in the last N turns: no file changed and no command produced new
output. If the task is complete, commit (if asked) and call finish(summary=...); otherwise
change your approach." and transcribe a `nudge` event; `"stalled"` → new terminal status
**`stalled`** with `final_message` `"no progress in <N> consecutive turns"`. `stall_turns=0`
disables detection. CLI: `--stall-turns N` (default 12) on `run` and `resume`.

Rationale for subsuming the ledger's detectors (b) and (c): identical `(tool, args)` calls
three times running are, for every tool, either read-only or bash-with-identical-output —
both already no-progress; "suite green but no commit" is exactly the situation the nudge
text addresses, and parsing test output to detect "green" would be tool- and language-
specific.

## 4. Context window

`Runner.__init__` gains `context_window: int | None = None`. Resolution, in
`resolve_context_window(model, flag_value, env_value) -> tuple[int, str]` (`runner.py`,
pure): flag > `DIRTYWORK_CONTEXT_WINDOW` env (must parse as a positive int, else the CLI
exits 2 with a message) > `CONTEXT_WINDOWS[model]` > `DEFAULT_WINDOW`; the second element
is the source (`"flag" | "env" | "table" | "default"`). When the source is `default`,
the CLI prints one stderr line:
`warning: no known context window for '<model>'; assuming 32768 tokens (set --context-window or DIRTYWORK_CONTEXT_WINDOW)`.
The resolved value is recorded in the `run_start` event as `context_window` and in
`run.json` as `context_window`. `--context-window` is a `run`/`resume` flag (positive int).
The `CONTEXT_WINDOWS` table stays as the fallback for the two known LM Studio models.

## 5. `dirtywork resume`

```
dirtywork resume <slug | run-dir> [--model M] [--max-turns N] [--timeout S] [--temperature T]
                 [--base-url U] [--stall-turns N] [--context-window N] [--image REF]
                 [--allow-network] [--memory] [--cpus] [--tmp-size] [--gitdir-size]
                 [--min-free-mb] [--keep-volume] [--max-patch-mb] [--max-worktree-mb] [--max-worktree-files]
```

A resume is a **new run** — new slug (`make_slug(task, now)`), run dir, transcript,
container and volume — on the **same worktree and branch** as the prior run.

**Lookup.** `<slug>` resolves to `~/.dirtywork/runs/<slug>`; a path containing `/` is a
run dir. `run.json` is read (`read_run_json`); the prior task comes from `run.json["task"]`
when present (SP2.5 starts writing it) else from the prior transcript's `run_start.task`;
likewise `model` (else `run_start.model`) and `turns` (else the last `run_end.turns`).
`--model` defaults to the prior run's model. `base_commit` must resolve in `repo`. A
setup failure on a resume never removes the worktree (it holds prior work).

**Refusals (exit 2, create nothing):**
- `run.json` missing/unreadable, or the transcript missing when `task` is not in `run.json`.
- prior `status == "running"` and `os.kill(host_pid, 0)` succeeds → "run <slug> is still in progress (pid N)"; a dead pid means a crashed run and resume proceeds.
- `worktree` missing, not a directory, or without a `.git` entry; or `base_commit` not resolvable in `repo`.
- `--sandbox` is not accepted on `resume`; the mode comes from `run.json["sandbox"]`. Docker mode additionally runs the same docker preflight as `run` (`--image` defaults to `run.json["image"]`).

**Task text.** `build_resume_task(prior_task, prior_status, prior_turns, transcript_tail) -> str`
(pure, `resume.py`):

```
<prior task text>

--- RESUMED RUN ---
This run continues an earlier run that ended with status '<status>' after <turns> turns.
The worktree already contains that run's work: inspect it with `git status` and `git diff`
before doing anything else, and continue from there — do not start over or revert prior work.
The last events of the earlier run were:
<transcript tail>
When the task is complete, call finish(summary=...).
```

`transcript_tail` = the prior transcript's `assistant`, `tool_result`, `nudge`, and
`run_end` events, newest last, rendered one per line as `assistant: <text[:1000]> [tools: a,b]`,
`tool_result <name>: <result[:500]>`, `nudge: <reason>`, `run_end: <status>`, taking events
from the end until the rendered text would exceed 12,000 chars (`RESUME_TAIL_CHARS`).

**Workspace.** Host mode: reuse the worktree as-is (`HostSandbox.start` needs nothing new).
Docker mode: `Sandbox.start(..., seed_from_worktree: bool = False)`; when true,
`DockerSandbox.start` calls `_init(restart=True)` (index at `base_commit`, no files
checked out) instead of `restart=False`, then streams the host worktree into `/work`:
`tar -C <worktree> --exclude=./.git -cf - .` piped through `docker exec -i <name> tar -C /work -xf -`
(both processes via the sandbox's `_popen`; bounded by a `T_LIFECYCLE` kill-timer like the
export streams; non-zero exit of either → `SandboxError("resume seed failed: …")`).
The in-container branch keeps the **original** host branch name: `init_worker_git`
gains a `branch: str` parameter (callers pass `f"dirtywork/{slug}"` today) so the resumed
container's `HEAD` is `refs/heads/dirtywork/<original-slug>` while its container/volume
names use the new slug. `check_name_collision` runs against the new slug. Export at the
end of a resumed docker run is unchanged: it flattens the final tree onto the same host
worktree. `export_run` requires an empty worktree (`.git` file only), so
`DockerSandbox.finalize` empties it with the existing `_cleanup_to_dot_git_only` immediately
before calling `export_run` when the sandbox was seeded from it. Export failure keeps the
volume for retry exactly as on a fresh run, so the worker's final state is never lost.

**Honest limit (documented in README):** docker export stores files, not the worker's
in-container commits; a resumed docker worker therefore sees the prior work as
uncommitted changes against `base_commit`, not as its old commit history. Host mode
keeps the real commits.

**Records.** New run's `run.json` gains `resumed_from: <prior slug>` and `task`; the
prior run's `run.json` gets a best-effort `resumed_by: <new slug>` (`_update_run_json`
semantics, never raises, does not touch `status` or `ended`). `run_start` event gains
`resumed_from`. Stdout JSON gains `resumed_from` (null for plain runs). `run.json` from
SP2.5 on always contains `task` and `model` at start and `turns` at end (plain runs too);
`load_prior_run` falls back to the transcript's `run_start`/`run_end` events for runs that
predate SP2.5.

## 6. `__main__.py` structure

`main()` becomes a thin dispatcher over stages that `run` and `resume` share:

- `_preflight_llm(args) -> client` (existing checks; exit 2 semantics unchanged),
- `_preflight_docker(args, repo)` (existing `_docker_preflight` + its error hints),
- `_workspace_new(args, repo) -> RunContext` (slug, branch, worktree creation, base commit — today's inline code),
- `_workspace_resume(args) -> RunContext` (§5 lookup/refusals; sets `seed_from_worktree`, `resumed_from`, `task`),
- `_execute(ctx, args, client) -> int` — everything from `ensure_runs_dir` to the final `print(json.dumps(...))`, parameterised by the context.

`RunContext` is a dataclass: `repo, slug, branch, worktree, base_commit, task, sandbox_mode, image_ref, image_digest, image_pinned, resumed_from, seed_from_worktree`. `run`'s observable behaviour (stderr lines, stdout JSON, exit codes, run.json) is unchanged except for the additive fields above; every existing `tests/test_main.py` test passes without modification.

## 7. Contract changes (all additive; `schema_version` stays 2)

- **Statuses:** `stalled` joins `max_turns`/`timeout`/… as a non-`completed` status (exit 1; worktree kept). README §Statuses/exit codes and SECURITY.md status lists updated. `_final_status` treats it like every other non-completed status.
- **Transcript events:** new `nudge` event `{"event":"nudge","kind":"truncated|empty|text_tool_call|stall","turn":N}`; `run_start` gains `context_window` and `resumed_from`; the `finish` call appears as an ordinary `assistant` tool call plus a `tool_result` with `result="run finished"`.
- **`run.json`:** gains `task`, `model`, `context_window`, `resumed_from` (new run), `turns` (at end), `resumed_by` (prior run).
- **stdout JSON:** gains `resumed_from`.
- **CLI:** `run` gains `--stall-turns`, `--context-window`; new `resume` subcommand (§5).
- **System prompt:** finish rule (§1.1).

## 8. Tests

- `tests/test_runner.py` (existing fake client/executor): `finish` ends the run after preceding calls execute; `finish` with missing summary; each `classify_text_reply` class and its nudge; `truncated` no longer completes; per-kind and total abort thresholds with kind-named messages; a success resets all kinds; stall nudge at N/2 and `stalled` at N; progress definitions (write success, new bash output, repeated bash output = idle, read-only = idle, `ERROR` result = idle); `stall_turns=0` disables; `context_window` resolution table with sources.
- `tests/test_resume.py`: `build_resume_task` tail truncation at `RESUME_TAIL_CHARS` and event rendering; refusal cases (running+alive pid, dead pid proceeds, missing worktree, sandbox switch); host-mode resume end-to-end on a temp repo with the fake LLM client (same harness `test_main.py` uses): second run reuses worktree/branch, `run.json.resumed_from`/`resumed_by`, prior `task` fallback to transcript when `run.json` lacks it.
- `tests/test_docker_lifecycle.py`/fakes: `init_worker_git(branch=…)` script contains the branch; `DockerSandbox.start(seed_from_worktree=True)` uses `restart=True` and issues the tar pipeline (fake popen).
- `tests/test_docker_live.py` (`-m docker`, runs in the CI `docker-live` gate): resume a completed docker run on a temp repo — the resumed container's `/work` matches the host worktree (a file the first run created is present, a deleted file is absent), `git symbolic-ref HEAD` is the original branch, and the final export succeeds.
- `tests/test_main.py`: `--stall-turns`/`--context-window` parsing; env precedence; unknown-model warning line; `resume` refuses `--sandbox`.

## Non-goals

- Reconstructing the exact prior message history on resume (the transcript truncates tool results; the tail is context, not replay).
- Reading the context window from LM Studio's server metadata.
- Reusing a kept volume on resume (a resume always seeds from the host worktree).
- Anything in SP3: tool registry, providers, `runs` commands, `bench`.
